Open Charge Point Protocol for Python

OCPP 1.6, 2.0.1 and 2.1, async and typed

An asyncio SDK for OCPP-J (OCPP over JSON/WebSocket), for both the Charge Point / Charging Station and the Central System / CSMS role. Every message is a Pydantic model generated from the official schemas and validated on send and receive.

Install #

The distribution is ocpp-sdk on PyPI and the import package is ocpp_sdk. It ships type hints (py.typed), is async-first on asyncio and has no sync API.

Quick start #

A CSMS and a station in one process, talking over loopback. The CSMS answers BootNotification; everything it does not handle is answered NotSupported.

OCPP 1.6 #

Messages #

The message models are generated from the official JSON schemas by tools/gen and are Pydantic v2 models. Python attributes are snake_case, the wire names are the spec's camelCase. Requests are <Action>Request and answers <Action>Confirmation; every class has an ACTION class variable. Enums are StrEnums with the spec's values.

ModuleMessages
ocpp_sdk.v16.coreAuthorize, BootNotification, ChangeAvailability, ChangeConfiguration, ClearCache, DataTransfer, GetConfiguration, Heartbeat, MeterValues, RemoteStartTransaction, RemoteStopTransaction, Reset, StartTransaction, StatusNotification, StopTransaction, UnlockConnector
ocpp_sdk.v16.firmwareDiagnosticsStatusNotification, FirmwareStatusNotification, GetDiagnostics, UpdateFirmware
ocpp_sdk.v16.localauthGetLocalListVersion, SendLocalList
ocpp_sdk.v16.reservationCancelReservation, ReserveNow
ocpp_sdk.v16.smartchargingClearChargingProfile, GetCompositeSchedule, SetChargingProfile
ocpp_sdk.v16.remotetriggerTriggerMessage
ocpp_sdk.v16.securitySecurity extension (whitepaper edition 3): CertificateSigned, DeleteCertificate, ExtendedTriggerMessage, GetInstalledCertificateIds, GetLog, InstallCertificate, LogStatusNotification, SecurityEventNotification, SignCertificate, SignedFirmwareStatusNotification, SignedUpdateFirmware

Shared datatypes and enums are in ocpp_sdk.v16.types. The security extension adds SecurityEvent (the whitepaper's event types), is_known_event and is_critical_event; SecurityEventNotification.type stays an open string because vendors may send other types. Certificates and CSRs are checked as PEM blocks of the right type (not parsed), certificate hashes as hex, and firmware signatures as Base64. Handlers: SecurityHandler and Config.security on both sides.

Spec beats schema. The GetInstalledCertificateIds answer may list no certificates: the spec says 0..*, the schema 1..*.

Incoming messages are validated on decode and outgoing ones on encode. Unknown properties are ignored (real stations send extras); everything else the schemas reject is rejected, plus the clear rules of the spec text: connectorId ranges, meterValue and chargingSchedulePeriod not empty, the first charging period starting at 0, charging limits with at most one decimal, a RemoteStartTransaction profile of purpose TxProfile, unique idTags (ignoring case) in SendLocalList with idTagInfo on every entry of a Full update, and absolute URIs for GetDiagnostics and UpdateFirmware. Naive datetimes are rejected; timestamps are sent in UTC with Z. An invalid incoming call is answered with the CALLERROR code that fits (1.6 spelling, OccurenceConstraintViolation included) and the offending field path.

Charge Point and CSMS #

ocpp_sdk.v16.charge_point.ChargePoint is the client and ocpp_sdk.v16.csms.CSMS the server; both are async context managers (see the quick start). Typed methods send each message and return the answer: await cp.boot_notification(BootNotificationRequest(...)) returns a BootNotificationConfirmation; every method takes an optional timeout=. The CSMS calls a station by ID, await csms.reset("CP-1", ResetRequest(...)), or through the session object (csms.ChargePoint) its handlers receive.

  • Handlers Each feature profile has a handler protocol per side (CoreHandler, FirmwareHandler, LocalAuthListHandler, ReservationHandler, SmartChargingHandler, RemoteTriggerHandler; the Central System receives only Core and Firmware) in ocpp_sdk.v16.charge_point_handlers and ocpp_sdk.v16.csms_handlers. Subclass the matching Unimplemented...Handler and override what you support; the rest answers NotSupported. Methods are on_<message>, sync or async; CSMS handlers get the session first. Wire them with the Config dataclass of each side; a profile left None answers NotSupported, an unknown action NotImplemented.
  • Errors A handler that raises answers InternalError (the exception text is never sent); raise ocpp_sdk.errors.CallError(code, description) to send a specific code. A CALLERROR from the peer raises CallError in the caller.
  • Offline Calls fail fast with NotConnectedError, also a call cut off by a lost connection. Nothing is queued or retried, and the station never sends BootNotification or Heartbeat on its own. ChargePoint reconnects per OCPP-J 5.4 (reconnect=Reconnect(...), None turns it off).
  • CSMS charge_point_ids(), charge_point(id), await for_each(fn) (identity order), on_connect/on_disconnect hooks, await shutdown(timeout=...). A station that reconnects gets a new session; the old session raises NotConnectedError. Every session whose on_connect hook returned gets exactly one on_disconnect, a replaced one too. If on_connect raises, the connection is closed (1011) and no on_disconnect follows.

Transaction message queue #

Opt-in and separate from ChargePoint (spec section 3.7): ocpp_sdk.v16.transaction_queue.TransactionQueue(charge_point, ...). Hand it StartTransaction, StopTransaction and MeterValues with start_transaction, stop_transaction and meter_values; it delivers them oldest first and waits while the station is offline (not a failure; ChargePoint.wait_online() is what it waits on).

  • Retries A message the Central System fails to process (CALLERROR, timeout, unusable answer) is tried up to attempts times (default 3), waiting retry_interval (default 60 s) times the number of earlier attempts, then dropped and reported to on_discard(action, request, reason).
  • Transactions start_transaction returns a Transaction handle: pass it as transaction= to the messages that belong to the transaction and they get the assigned transactionId when delivered (use any placeholder in the request); if the start is dropped they are dropped too. queue.join() waits until the queue is empty and queue.pending counts what is waiting.
  • Persistence The state lives in a TransactionStore: MemoryStore (default) or FileStore(path) (JSON file, replaced atomically on every change, so a restart picks up where it stopped). Saves made while delivering run in a worker thread, so a slow disk does not stall the event loop; a failing on_discard, a stored message that no longer validates or a failed save is logged and the queue keeps going.

OCPP 2.0.1 #

Same shape as 1.6, in ocpp_sdk.v201. The 64 messages are generated from the official schemas, one module per functional block (security, provisioning, authorization, localauthlist, transactions, remotecontrol, availability, reservation, tariffandcost, metervalues, smartcharging, firmware, iso15118, diagnostics, displaymessage, datatransfer), with the shared datatypes and enums in ocpp_sdk.v201.types. Names follow the schemas without their Type / EnumType suffix (IdToken, RegistrationStatus; the enum of an IdToken object is IdTokenEnum) and messages are <Action>Request / <Action>Response. customData keeps unknown vendor properties; other unknown properties are ignored. The quick start has a 2.0.1 example.

  • Classes ocpp_sdk.v201.charging_station.ChargingStation (client) and ocpp_sdk.v201.csms.CSMS (server; the session handed to its handlers is csms.ChargingStation), each with a Config that has one handler field per block the side receives (15 for the station, 13 for the CSMS). Handler protocols and Unimplemented... bases are in ocpp_sdk.v201.charging_station_handlers and ocpp_sdk.v201.csms_handlers; everything else (typed calls, NotSupported / NotImplemented / InternalError, offline behaviour, reconnect, for_each, hooks) works as for 1.6.
  • Rules beyond the schemas Clear statements of the spec text: evseId > 0 where required, a RequestStartTransaction profile of purpose TxProfile, transactionId in a profile only for TxProfile, valuesList for option, member and sequence lists, location for a Published firmware, SendLocalList Full with idTokenInfo on every entry, charging limits with one decimal, phaseToUse 1 to 3, monitoring severity 0 to 9. An optional list that is present must not be empty (the schemas' minItems).
  • Appendices ocpp_sdk.v201.appendices has the standardized components, variables, units, reason codes and security events of the appendices CSV files as constants (Component.AUTH_CTRLR, Unit.KWH, ReasonCode..., SecurityEvent...), the device model table and is_known_security_event / is_critical_security_event. Messages keep plain strings.

Examples: examples/v201/csms.py and examples/v201/charging_station.py, also tested against go-ocpp-sdk's 2.0.1 examples.

OCPP 2.1 #

In ocpp_sdk.v21, with the same shape as 2.0.1 and its own types (it does not import ocpp_sdk.v201, because ocpp2.1 is a different subprotocol): 91 messages in 19 functional-block modules (the 16 of 2.0.1 plus bidirectional, dercontrol and batteryswap), ChargingStation and CSMS in ocpp_sdk.v21.charging_station and ocpp_sdk.v21.csms, handlers in ocpp_sdk.v21.charging_station_handlers and ocpp_sdk.v21.csms_handlers, and the appendices constants in ocpp_sdk.v21.appendices (which also has the idToken types, connector types, charging limit sources, payment brands and recognitions, additionalInfo types and signing methods). idToken.type is a plain string in 2.1.

  • SEND and CALLRESULTERROR OCPP 2.1 adds two frame types that exist only on ocpp2.1 connections (they are unknown message types on the other versions). A SEND ([6, ...]) is an unconfirmed message: it is written at once, is not queued behind calls, may go out while a call is outstanding and is never answered. The one standard SEND message is NotifyPeriodicEventStream: await station.notify_periodic_event_stream(message). The CSMS receives SENDs through Config.send_handler(station, message) (sync or async), handled one at a time in arrival order from a bounded queue (the newest is dropped when it is full); a malformed or unknown SEND is only logged. The station's own Config.send_handler(message) is for vendor use. A CALLRESULT that cannot be decoded is answered with a CALLRESULTERROR; one received from the peer is logged. A CALL of a one-way message is answered ProtocolError.
  • Rules beyond the schemas Spec text and errata 2026-09: the 2.0.1 rules, V2X curves with at least two coordinates (and a freq-watt curve for LocalFrequency), randomizedDelay only for TxProfile and TxDefaultProfile, pctMaxDischargePower required and 0 to 100, PowerMonitoringMustTrip not as a stand-alone DER control, hv10MinMeanValue and hv10MinMeanTripDelay together, tariff conditions with 24h times and YYYY-MM-DD dates.

Examples: examples/v21/csms.py and examples/v21/charging_station.py (the station sends a periodic event stream), also tested against go-ocpp-sdk's 2.1 examples.

Transport #

ocpp_sdk.transport is version-agnostic. A Server and a Client hand every received text frame to a sink (anything with feed(raw) and async close(); ocppj.Endpoint is one). The high-level classes build on it; use it directly only for something custom.

  • The charge point ID is the last URL path segment (1-48 characters, no : or /). An invalid or unknown ID (known_id) answers HTTP 404.
  • The server picks the version by its own order of preference among the subprotocols the client offers (ocpp1.6, ocpp2.0.1, ocpp2.1). With no common one the handshake completes and the connection is closed with 1002.
  • A second connection with the same ID replaces the first (closed with 1008).
  • Compression is off, binary frames are refused (1003), ping every 30 s with a 10 s timeout, messages up to 1 MiB (1009 above that).
  • Server.shutdown(timeout) closes every connection with 1001, and a handshake that finishes during shutdown is closed with 1001 too.
  • Client reconnects as in OCPP-J section 5.4 (Reconnect(wait_minimum=1, random_range=2, repeat_times=6)): the wait applies after every lost connection and failed attempt, doubles up to repeat_times times, and resets after a successful connection. A missing common subprotocol counts as a failed attempt. reconnect=None makes one attempt.

Security profiles #

ProfileServerClient
1: Basic authauthenticate=fn(id, password) (401 on failure)password=...
2: TLS + Basic authssl_context=server_ssl_context(cert, key)ssl_context=client_ssl_context(cafile=...)
3: mutual TLSserver_ssl_context(..., client_ca=...) and check_certificate_identity=True (certificate CN must equal the ID, optionally O must contain operator_name; 403 otherwise) client_ssl_context(cafile, certfile, keyfile)

TLS 1.2 or newer, with ECDHE AES-GCM suites; TLS 1.0 and 1.1 are not supported.

The 1.6 Basic-auth password is the AuthorizationKey: 16 to 20 bytes as 32 to 40 hexadecimal digits, sent as that text. ocpp_sdk.transport.auth.check_authorization_key(key) validates one and generate_authorization_key() makes a new 40-digit key.

Core #

  • ocpp_sdk.errors OCPPError and its subclasses CallTimeoutError, NotConnectedError, QueueFullError, ValidationError and CallError; code sets ErrorCodeV16 (1.6 spelling) and ErrorCodeV2 (2.0.1 and 2.1).
  • ocpp_sdk.datetime parse and format for every version. Naive datetimes are rejected.
  • ocpp_sdk.ocppj Endpoint correlates calls, enforces timeouts (30 s from send), sends one CALL at a time with a bounded queue of 1,000, answers handler errors with InternalError (the exception text is never sent), and fails waiting calls with NotConnectedError when the connection ends. Nothing is queued or retried while offline.

Error handling #

All exceptions derive from ocpp_sdk.errors.OCPPError.

ExceptionWhen
NotConnectedErrorNo connection, or the connection was lost during the call. Nothing is queued or retried.
CallTimeoutErrorNo answer within the timeout (30 s from the moment the call was sent).
CallErrorThe peer answered with a CALLERROR (.code, .description, .details); also what a handler raises to send one.
ValidationErrorA request or an answer is invalid (.issues lists field paths).
QueueFullErrorMore than 1,000 calls are waiting behind the outstanding one.

Logging #

The SDK logs through the standard logging module under ocpp_sdk.* (ocpp_sdk.ocppj.endpoint, ocpp_sdk.transport.server, ocpp_sdk.v16.csms, ...). It never configures handlers or levels, so call logging.basicConfig(level=logging.INFO) or attach your own. The WebSocket library logs as ocpp_sdk.transport.websockets. Message payloads are not logged.
